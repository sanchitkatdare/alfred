Project alfred · design review · 3 Oct 2026

Alfred architecture

A reusable agent harness, shown through a movie recommender and a pantry planner. Rules handle most requests in the browser. Embeddings handle free text. An LLM runs only for multi-step tasks.

Current assessment

The design is consistent and much simpler than the first prompt. Hosting costs nothing. Most requests make no LLM call, and the UI shows every routing decision. The open risks are Workers AI tool-calling quality, the daily free quota, and real latency. A one-hour spike can test all three.

      Decision model

      How a request is routed

      Our code makes the decisions. A request moves to a higher level only when the lower level cannot handle it.

      Level 1RouterBrowser

      Rules match genres, people, runtime, year, rating, negation and task words. Words left over decide the outcome.

      No leftover words: filter locally. Descriptive words left over: semantic search. Task words: escalate. On submit, an embedding compares the query with example phrases for each intent. The rules may be unsure. In that case, this check finds the intent.

      0 AI callsor 1 embedding
      ↓ task matches a known workflow
      Level 2WorkflowsBrowser

      Fixed steps written in code. Example: meal plan. Read pantry, search recipes, compute missing ingredients as a set difference, write the shopping list.

      The LLM writes the summary text only. This step is optional.

      0-1 LLM calls
      ↓ open-ended task, or low confidence
      Level 3Agent loopBrowser + Workers AI

      The LLM proposes tool calls. The harness checks that each tool is allowed and validates the arguments. Then it runs the tool. It sends any validation error back to the LLM, and it stops after 5 iterations.

      2-5 LLM calls

      What the tasks cover

      How each model failed

      ModelFailure patternFix
      granite-4.0-h-microPut genres and negations in free text ("no horror") instead of filtersParser hints: the rule parser's chips become hard filters. Raised the pass rate from 81% to 93%.
      granite-4.0-h-microSometimes answers without calling a toolOpen: force a tool call on the first turn, or retry once
      qwen3-30b-a3b-fp8Answers from memory, skipping toolsNone found. Not chosen.
      glm-4.7-flash, gemma-4-26b-a4b-itAccurate, but slow outliers of 25-44 sNot fixable on our side
      All modelsMalformed tool arguments made Workers AI reject the conversationHarness bug, fixed: malformed arguments are sent back as {}

      Decision and trade-off

      granite-4.0-h-micro with parser hints. It gives up a few points of accuracy against gemma (93% versus 100%) in exchange for about 3.5 times more assistant tasks per day within the free quota, and answers that are about twice as fast, with a p90 of 8.3 s instead of 18.9 s. That matches the project's goals of zero cost and instant answers. The rule parser covers granite's main weakness. gemma-4-26b-a4b-it is the quality fallback; switching is one line.

      Re-run pnpm compare-models when tools or prompts change, a new task type is added, a model is deprecated, or prices change.
